TRACK A — HEALTH & MOTOR CLAIMS  |  PROJECT A1  |  DIFFICULTY: MEDIUM
Cashless Pre-authorisation Agent (NHCX-aligned)
Team Capstone Implementation Plan — 3-Member Work Breakdown
1. Problem
India's IRDAI Master Circular on Health Insurance Business (May 2024) turned cashless authorisation into a hard, timed compliance obligation: pre-authorisation decisions must be made within one hour of a hospital's request, and final discharge authorisation within three hours. Missing that clock is not a service lapse — it is a regulatory breach.
Today, most of that first-touch decision is mechanical rather than judgment-heavy: read the hospital's pre-auth request, locate the correct policy wording and any endorsements, check waiting periods, sub-limits, room-rent capping, co-pay and exclusions, and confirm the admission date falls inside the policy period. Because this is done manually and under time pressure, two adjudicators can reach different conclusions on identical facts, and customers experience repeated “please send one more document” cycles — the single largest driver of poor claims experience and Ombudsman complaints.
The problem this project solves: build an agent that performs this mechanical first pass — ingest, extract, retrieve the governing clause, apply the rule, and produce a defensible, cited recommendation — fast enough to fit inside the regulatory window, while a human remains the only party who actually authorises or denies a claim.
2. Contribution
The team will design and build an end-to-end, recommend-only agentic pipeline that:
	•	Ingests a hospital cashless pre-authorisation request (synthetic, NHCX/FHIR-style payload — PDF, scanned image or structured JSON).
	•	Extracts a structured clinical and financial record (patient/policy IDs, diagnosis, procedure, estimated cost, admission type, hospital details) into a validated Pydantic schema.
	•	Retrieves the applicable benefit structure and policy clauses — waiting periods, sub-limits, room-rent capping, co-pay, deductibles, exclusions, the IRDAI non-payables list.
	•	Reasons against those clauses to produce one of three recommendations — Authorise / Query / Deny — never an automatic decision.
	•	Shows the arithmetic and cites the exact clause behind every capping or deduction.
	•	Routes low-confidence, high-value or clause-ambiguous cases to a human reviewer queue, and logs every step to an immutable audit trail.
	•	Is evaluated on turnaround time against the regulatory clock, extraction and retrieval quality, grounding fidelity, decision accuracy and behaviour on adversarial inputs.
This is a “recommend, never decide” system in line with the governance guardrails in Section 8 — a human always signs off before any real authorisation or denial is issued.

4. Tech Stack
4.1 Shared foundation (all members)
	•	Language & environment: Python 3.11, Git/GitHub, virtualenv or Poetry
	•	Schema & validation: Pydantic v2 (structured extraction, decision object, audit record)
	•	Agent orchestration: LangGraph (recommended for explicit state machine + human-in-the-loop nodes) or CrewAI as an alternative — pick one and justify in the report
	•	LLM access: Claude or GPT via API for extraction/reasoning; optionally one open-weight model (e.g. Llama/Mistral class) for the deployment-note cost/quality comparison
	•	Document parsing: pdfplumber / PyMuPDF for text PDFs, Tesseract or PaddleOCR for scanned pre-auth forms
	•	Data interchange target: FHIR-style JSON, aligned to NHCX's claim exchange structure rather than a bespoke schema
4.2 Member-specific tooling
Member 1 — Data & Extraction
	•	Synthetic data: LLM-assisted generation + Faker for identifiers; a documented generator script (governance guardrail: synthetic data only)
	•	Extraction: LLM function-calling / structured-output mode, validated against Pydantic schemas; OCR post-processing for scanned inputs
Member 2 — Retrieval & Orchestration
	•	Vector store: FAISS or Chroma; embeddings via OpenAI/Cohere/local sentence-transformers
	•	Rules engine: Python rule objects or a lightweight DSL for waiting period / sub-limit / co-pay / room-rent capping logic
	•	Mock core systems: FastAPI stub endpoints simulating the policy admin and claims systems (tool-calling targets)
Member 3 — Evaluation, Governance & Interface
	•	Evaluation: pytest + pandas scoring notebook/script against the golden test set
	•	Audit log: append-only store (SQLite or hash-chained JSON lines) for tamper-evidence
	•	Demo/UI: Streamlit (fastest) or FastAPI + a minimal React front end for the reviewer queue and audit trail viewer

7. Outcome
Success is measured the same way an insurer's risk and operations committees would measure it:
	•	Turnaround compliance — share of pre-auth recommendations produced inside the 60-minute window (the metric with direct regulatory impact).
	•	First-touch handling time reduced 30–50% on a fixed claim mix, before vs. after.
	•	A defined band of low-value, low-complexity claims handled straight-through with only a human spot-check.
	•	One-and-done document requests — completeness gaps identified in a single query instead of two or three rounds.
	•	Decision consistency — reduced variance in recommendations across the same scenario set.
	•	Leakage reduction — sub-limits, capping and exclusions applied correctly under time pressure.
	•	Auditability — 100% of deductions carry a clause-level citation; a fabricated or misattributed citation is a critical failure, not a minor one.
8. Governance Guardrails (mandatory)
These apply to every one of the 17 capstone teams and are graded, not optional framing:
	•	Recommend, never decide — the agent never auto-authorises or auto-denies. Be ready to explain why this is both the safe and the regulatorily coherent design.
	•	Grounded output or no output — every coverage conclusion or deduction cites a retrieved clause or source page; a fabricated citation is a critical failure.
	•	Synthetic data only — no real policyholder or claimant data, under any circumstances; document the generator.
	•	Deployment note — a one-page analysis of where the model runs, what data crosses which boundary, and the cost of an India-hosted or open-weight alternative.
	•	Fairness — decisions rest only on risk-relevant, cited rules, never on proxies for religion, caste, region or gender inferred from name, address or PIN code.
	•	Cite the live text — every regulatory claim cites the current instrument on irdai.gov.in with its date; working from a stale summary (including this brief) is itself an error.
	•	Human-in-the-loop — define explicitly what triggers escalation, what the human reviewer sees, and how a human override is captured for future improvement.
9. Evaluation Rubric
Report all nine numbers on a shared golden test set of at least 100 cases, of which at least 30 are deliberately adversarial:
Dimension
What to measure
Extraction accuracy
Field-level precision and recall on the structured record
Retrieval quality
Was the governing clause actually retrieved? Recall@k
Grounding fidelity
% of assertions traceable to a real source; hallucinated-citation rate
Decision accuracy
Agreement with the expert-labelled ground truth
Escalation precision
Did it escalate what it should, and only that?
Latency
End-to-end time, against the 1-hour / 3-hour regulatory clock
Cost
Tokens and rupees per transaction — decides viability at Indian claim volumes
Robustness
Behaviour on malformed, adversarial and out-of-distribution input
Fairness
Outcome stability when protected-proxy attributes are perturbed

Mandatory adversarial cases
	•	An expired or lapsed policy
	•	A claim that falls inside a waiting period
	•	A duplicate submission with a transposed digit
	•	An endorsement that reverses the base wording
	•	A document in an unexpected language
	•	An illegible scan
	•	A claim that falls just either side of a sub-limit or waiting-period threshold
	•	A prompt-injection attempt embedded in an uploaded document
Report both error directions — a system that never misses a suspicious claim but over-queries 40% of honest ones is not a good system. Make the trade-off visible in the numbers, not just in prose.

10.3 Common pitfalls to avoid
	•	Designing the extraction schema around one sample hospital form instead of the NHCX/FHIR structure — revisit this before Week 3 if it hasn't been checked against the real standard.
	•	Letting the agent silently auto-decide in code even though the report says “recommend-only” — the escalation/human-approval step must be a real, non-bypassable node in the graph.
	•	Citing a clause that was never actually retrieved (hallucinated citation) — this is graded as a critical failure, so wire citation-to-source verification into the reasoning node itself, not just into the eval script.
	•	Building the evaluation harness only in Week 11 — start scoring against a small golden set from Week 4 so the whole team sees real numbers, not vibes, well before the deadline.
	•	Treating the deployment note as an afterthought — it's a two-paragraph decision with real trade-offs (latency and cost of India-hosted/open-weight models vs. an overseas API); allocate real time to it in Week 11.
